## 5. FEATURE SPEC 1 — DELEGATED SPENDING LIMITS (UPI Reserve Simulation)

**Location:** `apps/agent-service/services/wallet_service.py` + `transaction_service.py`

**Business rule:** guardrail threshold is `SPEND_LIMIT_PAISE = 500000` (₹5,000), configurable via env. Transactions `<= limit` execute autonomously. Transactions `> limit` create an `otp_challenges` doc and return `202 awaiting_otp` — **the transaction must not touch wallet balance until OTP is verified.**

**This endpoint is the single source of truth for spending enforcement in the entire system.** Every caller — the raw API, the MCP checkout flow, and Onyx's LLM tool-calling loop (Section 9) — must route actual money movement through this same code path. No caller, including the LLM orchestrator, is trusted to self-enforce the limit.

**You must implement, precisely:**

1. **Idempotency / replay-attack prevention:** every call to `POST /api/transactions/execute` requires a client-generated `idempotencyKey`. Before doing anything else, query `transactions` by that key. If it exists, **return the stored result verbatim** — do not re-debit, do not re-call Razorpay. Enforce this at the DB level too via the unique index (catch the duplicate-key error as a second line of defense, not the only one).

2. **Optimistic concurrency control (the core anti-bypass mechanism):** debiting the wallet must use a single atomic `find_one_and_update`:
```python
   db.wallets.find_one_and_update(
     { 'agentId': agentId, 'version': currentVersion, 'balancePaise': { '$gte': amountPaise } },
     { '$inc': { 'balancePaise': -amountPaise, 'version': 1 } },
     return_document=pymongo.ReturnDocument.AFTER
   )
```
   If this returns `None`, another concurrent transaction already mutated the wallet (version mismatch) — **retry** by re-reading the wallet and its current `version`, up to 5 attempts with jittered exponential backoff (base 20ms, factor 2, ±30% jitter). If retries are exhausted, fail explicitly with reason `CONCURRENT_MODIFICATION_MAX_RETRIES` — never silently allow the debit to skip the guardrail check.
3. **The guardrail check (`amountPaise <= SPEND_LIMIT_PAISE`) is evaluated fresh on every attempt** against the actual value being debited — do not cache the decision from a prior read, and do not let any caller (including Onyx) pass a pre-computed "guardrail already passed" flag into this function.
4. Wrap the debit + transaction-doc-insert + Razorpay TEST order creation in a **MongoDB multi-document ACID session/transaction** (`with client.start_session() as s: s.with_transaction(...)`), so a Razorpay API failure after debit cannot leave the wallet decremented with no corresponding record.
5. OTP path: generate a 6-digit numeric OTP, `bcrypt`-hash it before storing, and return it in the API response **only when `DEV_MODE=true`**, clearly commented `# DEV ONLY: in production this is sent via SMS/push, never returned in the API response`. Verifying consumes an attempt; after 3 failed attempts, reject the transaction and expire the challenge.
6. Emit `audit_logs` entries at every step (`GUARDRAIL_PASS` or `GUARDRAIL_OTP_REQUIRED`, then `OTP_VERIFIED`, then `ORDER_GENERATED`) and push each one through `ws_client.py` to the ws-gateway immediately (do not batch).

## 6. FEATURE SPEC 2 — MACHINE-READABLE MCP CATALOG

**Location:** `apps/mcp-server/`

**Business rule:** Express server exposing the catalog and checkout as MCP-style JSON-RPC 2.0 tools over `POST /mcp`, seeded with exactly 20 realistic items (`scripts/seedCatalog.ts` — real product names/prices/categories, not `item1`, `item2`).

- `get_item(sku)`
- `create_order(items: [{sku, qty}], buyerAgentId, idempotencyKey)`
- `get_order_status(orderNumber)`

**You must implement, precisely:**

1. **Inventory race-condition patch:** stock decrement on `create_order` must be a single atomic Mongo operation per item:
```typescript
   CatalogItem.findOneAndUpdate(
     { sku, stock: { $gte: qty } },
     { $inc: { stock: -qty, reservedStock: qty, version: 1 } },
     { new: true }
   )
```
   If it returns `null`, stock was insufficient at the moment of the atomic check — return `{ code: -32001, message: "INSUFFICIENT_STOCK", data: { sku } }` and **roll back any items already decremented earlier in the same multi-item order** inside a Mongo transaction (all-or-nothing checkout).
2. **Duplicate checkout prevention:** `orders.idempotencyKey` is unique-indexed. On duplicate-key error (`E11000`), catch it, fetch the existing order by that key, and return it instead of creating a second one.
3. **Endpoint security / rate limiting:** every `/mcp` and REST request requires header `X-API-Key`, hashed and looked up in `api_clients`. Apply `express-rate-limit` **per API key** (not per IP), default 60 req/min, configurable per client, returning JSON-RPC error `-32029 RATE_LIMITED` with a `Retry-After` header. Also apply `helmet()` and a body-size limit (100kb).
4. Provide a plain REST fallback (`GET /catalog`, `GET /catalog/:sku`, `POST /orders`) calling the same underlying service functions as the MCP tools — no duplicated business logic.
