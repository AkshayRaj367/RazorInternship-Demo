   267→## 5. FEATURE SPEC 1 — DELEGATED SPENDING LIMITS (UPI Reserve Simulation)
   268→
   269→**Location:** `apps/agent-service/services/wallet_service.py` + `transaction_service.py`
   270→
   271→**Business rule:** guardrail threshold is `SPEND_LIMIT_PAISE = 500000` (₹5,000), configurable via env. Transactions `<= limit` execute autonomously. Transactions `> limit` create an `otp_challenges` doc and return `202 awaiting_otp` — **the transaction must not touch wallet balance until OTP is verified.**
   272→
   273→**This endpoint is the single source of truth for spending enforcement in the entire system.** Every caller — the raw API, the MCP checkout flow, and Onyx's LLM tool-calling loop (Section 9) — must route actual money movement through this same code path. No caller, including the LLM orchestrator, is trusted to self-enforce the limit.
   274→
   275→**You must implement, precisely:**
   276→
   277→1. **Idempotency / replay-attack prevention:** every call to `POST /api/transactions/execute` requires a client-generated `idempotencyKey`. Before doing anything else, query `transactions` by that key. If it exists, **return the stored result verbatim** — do not re-debit, do not re-call Razorpay. Enforce this at the DB level too via the unique index (catch the duplicate-key error as a second line of defense, not the only one).
   278→
   279→2. **Optimistic concurrency control (the core anti-bypass mechanism):** debiting the wallet must use a single atomic `find_one_and_update`:
   280→```python
   281→   db.wallets.find_one_and_update(
   282→     { 'agentId': agentId, 'version': currentVersion, 'balancePaise': { '$gte': amountPaise } },
   283→     { '$inc': { 'balancePaise': -amountPaise, 'version': 1 } },
   284→     return_document=pymongo.ReturnDocument.AFTER
   285→   )
   286→```
   287→   If this returns `None`, another concurrent transaction already mutated the wallet (version mismatch) — **retry** by re-reading the wallet and its current `version`, up to 5 attempts with jittered exponential backoff (base 20ms, factor 2, ±30% jitter). If retries are exhausted, fail explicitly with reason `CONCURRENT_MODIFICATION_MAX_RETRIES` — never silently allow the debit to skip the guardrail check.
   288→3. **The guardrail check (`amountPaise <= SPEND_LIMIT_PAISE`) is evaluated fresh on every attempt** against the actual value being debited — do not cache the decision from a prior read, and do not let any caller (including Onyx) pass a pre-computed "guardrail already passed" flag into this function.
   289→4. Wrap the debit + transaction-doc-insert + Razorpay TEST order creation in a **MongoDB multi-document ACID session/transaction** (`with client.start_session() as s: s.with_transaction(...)`), so a Razorpay API failure after debit cannot leave the wallet decremented with no corresponding record.
   290→5. OTP path: generate a 6-digit numeric OTP, `bcrypt`-hash it before storing, and return it in the API response **only when `DEV_MODE=true`**, clearly commented `# DEV ONLY: in production this is sent via SMS/push, never returned in the API response`. Verifying consumes an attempt; after 3 failed attempts, reject the transaction and expire the challenge.
   291→6. Emit `audit_logs` entries at every step (`GUARDRAIL_PASS` or `GUARDRAIL_OTP_REQUIRED`, then `OTP_VERIFIED`, then `ORDER_GENERATED`) and push each one through `ws_client.py` to the ws-gateway immediately (do not batch).
